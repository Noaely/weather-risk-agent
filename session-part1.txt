  Where I think CLAUDE.md is wrong or risky

  Data sources

  A. Open-Meteo is modelled data, not station measurements. The historical API
  is built on ERA5 reanalysis, a grid of roughly 9–25 km. In practice:
  - Wind gusts: a grid this coarse smooths out thunderstorm gusts, so most hubs
    will show close to zero days ≥ 75 km/h. The wind metric will be weak.
  - Heavy rain: daily totals are smoothed, so heavy-rain days come out lower
    than at a rain gauge.
  - Snowfall is estimated by the model, not measured. "% of days in Denver with
    snowfall" may differ from the NWS figure for Denver airport.
  - What I'll do: in Stage 1, compare one hub-year against published NWS climate
    figures to see how far off it is. The agent will say "modelled data" in its
    data_sources and assumptions. Station data (NOAA GHCN-Daily) goes under
    Future work.

  B. Open-Meteo's free tier is for non-commercial use only. That's fine for a
  home assignment, but a real logistics client would need the paid plan. This
  will go in the limitations section.

  C. FEMA NRI scores reflect what's at stake, not just how bad the weather is. I
  think this is the biggest data risk.
  - The NRI *_RISKS score combines expected annual loss in dollars with social
    vulnerability and community resilience.
  - Very large counties score high on almost everything because they hold so
    much population and property. That includes Cook (Chicago), Harris
    (Houston), Dallas, and Maricopa (Phoenix).
  - So Phoenix may not come out as the low-risk contrast on the NRI layer.
  - Social vulnerability measures resident populations, which isn't relevant to
    a warehouse.
  - Proposal: use NRI's hazard-specific annualized frequency (*_AFREQ) or the
    building loss rate (*_ALRB). Both are adjusted for the size of the county.
    I'll check the exact field names and values in Stage 1 before choosing.

  D. NRI edge cases:
  - Several hubs span more than one county (Kansas City, Dallas, Houston). I'll
    use the county with the most of the city in it and document that.
  - Hurricane and coastal flood come back as "not applicable" for inland
    counties. I'll treat those as 0, not missing. Otherwise Chicago's hurricane
    score would become "I don't know".
  - I'll download NRI once as a county CSV into data/raw/ and record the version
    and download date. I'll check whether a usable API exists, but I don't
    expect one.

  E. NWS alerts (bonus): api.weather.gov needs a User-Agent header. I'll use a
  generic app name, not your email.

  Scoring thresholds and logic

  F. One calendar year is too small a sample to score on. A single year is very
  noisy:
  - The calendar year splits two winters in half.
  - Miami may have had no hurricane in 2025.
  - Houston's 2021 freeze would be invisible in most years.
  - Proposal: score on a 10-year average (2016–2025). That's still one cheap
    Open-Meteo call per hub. Factual questions ("last year in Denver") still
    use 2025. CLAUDE.md already allows this with "unless stated otherwise", but
    it's a change in meaning, so I need your OK.

  G. The hurricane score has to lean on NRI. Wind-gust days can't measure
  hurricane exposure, for the reasons in A and F. I'd weight hurricane as
  roughly 75% NRI and 25% gust days. Winter and flood can split more evenly.

  H. Fixed thresholds need two anchor points per metric. For each metric I need
  the raw value that maps to 0 and the raw value that maps to 100. Scores are
  clamped and linear in between, for example 0 days of ≥1 in snow → 0 and 20
  days → 100. CLAUDE.md doesn't say how these anchors are chosen.
  - If they're badly placed, every hub ends up near 0 or stuck at 100.
  - In Stage 3 I'll print each metric's spread across the hubs so we can set the
    anchors together. They'll be set from climate reasoning, not fitted to
    these 12 hubs.

  I. Averaging NRI scores with our own scores mixes two kinds of number. An NRI
  score is a national percentile; ours are linear scales. Averaging them is
  defensible but it's an assumption, and it goes in the docs.

  J. The overall score can hide a single extreme hazard. Miami could have 95 for
  hurricane and 0 for winter, giving an overall score of about 45, which looks
  "moderate". I'd show both the weighted average and the worst single hazard,
  and rank by hazard when the question names one.

  K. Specific thresholds:
  - ≤ −15 °C: fine as an explicit assumption.
  - Ice and freezing rain: this is the real winter risk in Dallas, Memphis and
    Atlanta, and none of our metrics capture it. NRI does have Ice Storm,
    Tornado and Hail columns.
  - Proposal for those columns: store them as context-only, not scored, so the
    Dallas answer can cite real NRI figures for tornado and hail instead of a
    vague "might be". This is a small scope expansion, so I need your yes or no.
  - "% of days" vs "count of days": I'd score on count of days. It's the same
    thing over a fixed period and easier to read.

  L. The Dallas eval can't assume the answer. The test question assumes the
  score is high, but we don't know what we'll compute. The eval case will be:
  "if the computed score is below high, the answer must say so and show the
  breakdown."

  Opus or Sonnet for the demo

  Short answer: yes, Sonnet 5.5 is good enough here. I'd make it the default and
  keep the model as a config setting.

  Why it fits this task:
  - All the hard work (numbers, rankings, breakdowns) happens in our Python
    tools, so the model only has to do three things:
    - pick the right tool
    - pass the right arguments
    - explain what came back
  - That's routing and explaining, not hard reasoning, and it's where the
    smaller model gives up the least quality.
  - The parts that need more care are not taking the Dallas false premise at
    face value and saying "I don't know" when a tool returns nothing. The eval
    covers both.

  Latency is mostly about how many round trips each question takes, not just the
  model:
  1. Fewer, bigger tool calls. compare_hubs(["Miami","Houston"],
     ["hurricane","flood"]) answers in one call instead of four. I'll design
     each tool so a typical question needs one or two calls plus submit_answer.
  2. Parallel tool calls. When Claude asks for several tools in one turn, the
     backend runs them all and sends the results back together.
  3. Prompt caching. The system prompt and tool definitions are the same on
     every request, so they get cached. That cuts time-to-first-token on every
     round trip.
  4. Lower effort or no thinking. For a Q&A agent like this, low or medium
     effort is usually enough. Sonnet 5.5 can also turn thinking off
     (between_tools mode), which Opus 5.5 can't. I'll measure this rather than
     assume it.

  One thing doesn't change with the switch: Sonnet 5.5 also rejects forcing a
  specific tool call. So the submit_answer design from my plan stays as it is:
  strict schema, a system prompt telling it to finish with that tool, Pydantic
  validation, and one retry.

  How I'll settle it:
  - Config: AGENT_MODEL and AGENT_EFFORT in .env, read by
    backend/agent/config.py. Default is claude-sonnet-5-5 at medium.
  - Stage 6: the eval runner will take --model and print pass rate plus median
    and slowest response time.
  - The comparison: I'll run the eval on Sonnet at low and medium effort and on
    Opus at medium, then show you the table. If Sonnet passes everything, it's
    the demo model. If it fails cases Opus passes (most likely the false-premise
    or "I don't know" cases), we decide with real numbers.
  - Backup for the live demo: a --warm flag to pre-run the 4 example questions
    so the first request isn't slow.
